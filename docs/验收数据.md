## 第 4 项补充：后端离线期间的消息有没有丢（比指标本身更能说明问题）

场景：后端订阅进程**完全停止** → 从 EMQX WebSocket 客户端连发 3 条 QoS1 消息 → 重新启动后端。

| 观测点 | 结果 |
|---|---|
| 重启后是否立刻收到离线期间的 3 条 | ✅ 是，`a-002 / a-003 / a-004` 在 `[connect]` 之后**立即连续**打印，无需再发 |
| 到达顺序 | ✅ 按发送顺序 002 → 003 → 004，未乱序 |
| 依赖的机制 | 固定 `client_id="server-sub"` + `clean_session=False`，broker 为离线会话保留队列 |
| 反证 | 若用 `clean_session=True`，这 3 条会永久消失（设备已收到 PUBACK，不会重发） |

> 这条不是手册里的验收项，是**自己加的一条**——因为"设备侧补传"只覆盖"设备断网"，
> 覆盖不了"后端重启"。面试讲可靠性时，这两层能一起说。

## 第 8 项：加索引前 vs 加索引后（这一项单独做，面试最爱问）

10 万条基准数据（独立 `data/bench.db`，不污染主库），每项跑 5 次取中位数。

### 场景 A：窄时间窗查询（看板真正用的）—— 索引的主场

```sql
SELECT * FROM reading WHERE node_id='bench' AND ts BETWEEN ? AND ? ORDER BY ts DESC LIMIT 500
```

| | 执行计划 | 5 次耗时（ms） | 中位数 |
|---|---|---|---|
| 加索引前 | `SCAN reading` | 11.7 / 12.1 / 13.2 / 13.2 / 13.4 | **13.2 ms** |
| 加 `(node_id, ts)` 后 | `SEARCH reading USING INDEX idx_reading_node_ts` | 0.4 / 0.4 / 0.4 / 0.7 / 0.9 | **0.4 ms** |

**加速 33.2 倍**（13.2 → 0.4 ms），建索引耗时 44 ms。

### 场景 B：全区间聚合（反例）—— 索引反而更慢

```sql
SELECT COUNT(*), AVG(t) FROM reading WHERE node_id='bench'
```

| | 执行计划 | 中位数 |
|---|---|---|
| 加索引前 | `SCAN reading` | **11.1 ms** |
| 加索引后 | `SEARCH ... USING INDEX` | **14.5 ms（0.77 倍，变慢）** |

**为什么变慢**：① 条件覆盖全表，索引无法减少行数；② `AVG(t)` 需要 `t` 列，
而索引里只有 `(node_id, ts)` → 每行都要回表，顺序扫反而更快。

**结论一句话**：**索引只对「能缩小扫描范围」的查询有用；对全表聚合，它带来的回表开销会让查询变慢——索引不是越多越好。**
