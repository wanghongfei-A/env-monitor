# 需求说明 · 环境监测与远程告警系统

> 版本 v0.1　作者：王宏飞　日期 2026-11-18

## 1. 背景：现在是什么样

- 场景：学校宿舍，4 人合住约 18㎡，朝南，有空调
- 现状：温湿度、光照全靠人工，一天看 2 次
- 具体会出什么事：空调忘关（开一整夜，电费+早上嗓子干）、充电器/路由器堆的柜子发烫、白天灯一直亮着
- 痛点量化：问题平均滞后 4 小时才发现。上周发生过吗？没有记录

## 2. 三项定义（写完就不改；真要改，走第 5 节变更记录）

| 项    | 定义                                                           | 为什么这么定（你必须自己写理由）                                                          |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 采集频率 | 10 秒 / 次                                                     | 日均 8640 条。为什么不是 1 秒？为什么不是 1 分钟？DHT22 最快 2 秒更新一次，10 秒采样已经比它快 5 倍；再快只是拿到重复值 |
| 告警规则 | 温度 > 32℃ 连续 3 分钟<br>湿度 > 85% 连续 5 分钟<br>光照 > 300lux 连续 30 分钟 | 为什么必须「连续 N 次」而不是「越限一次就报」？答：忘关灯告警：lux > 300 持续 30 分钟（白天）→ 灯白开着。宿舍忘关灯。      |
| 告警方式 | 钉钉群机器人，越限后 5 秒内送达                                            | 为什么选钉钉？免费且能够@人                                                            |



1. 阈值：手册给的是 32℃ / 85% / 50lux。我实际用 32℃ / 85% / 300lux，因为我这个场地 空调忘关（开一整夜，电费+早上嗓子干）、充电器/路由器堆的柜子发烫、白天灯一直亮着。
2. 连续时长：手册是 3 / 5 / 10 分钟。我沿用 / 调整为 ______，理由是 ______。
3. 本地要不要也响？蜂鸣器只在「本机还在线但服务端判越限」时没用（判断在云端），
   所以本地蜂鸣器的定位是： 必须保持一致，固件里也判一次温度，因为断网时云端判不了，本地蜂鸣器是唯一还能报警的通道。

## 3. 验收指标（来自实施手册 1.5，实测值最后填在 docs/验收数据.md）

| #   | 指标            | 目标值                  |
| --- | ------------- | -------------------- |
| 1   | 单节点日采集量       | 8640 条               |
| 2   | 端到端 P95 延迟    | < 2 s                |
| 3   | 消息丢失率         | < 0.5%               |
| 4   | 重复入库率         | 0                    |
| 5   | 断网 10 分钟补传完整率 | 100%                 |
| 6   | 告警送达时延        | < 5 s                |
| 7   | 连续运行时长        | ≥ 7 天                |
| 8   | 10 万条查询耗时     | < 200 ms（需给出加索引前后对比） |
| 9   | 单节点物料成本       | < 150 元              |

验收第 6 项「< 5 秒」指的是 规则判定成立的那一刻 → 钉钉收到消息，不包含前面 3 分钟的连续观察窗口。所以温度从越限到手机响，最坏情况是 3 分钟 + 5 秒。

连续判定的实现：10 秒一条，3 分钟 = **18 条**，5 分钟 = **30 条**，10 分钟 = **60 条**。
